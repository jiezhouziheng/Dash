# Life Graph AI 助手开发日志

日期：2026-06-02

分支：`feature/ai`

仓库：`D:\programAndCoding\courseproj-lifegraph\life-graph`

目标：在 Life Graph 移动端中实现一个可运行的 AI 助手 MVP。第一版采用“移动端本地 Agent 执行工具 + FastAPI 后端承载 LLM 调用”的架构，避免后端直接访问手机本地 SQLite 数据。

---

## 1. 开发约束与总体思路

本轮开发一开始明确了一个重要协作约束：所有项目代码修改都由开发者手动执行，AI 只负责给出每一步代码、解释、检查结果和问题诊断。因此开发过程采用了“先读项目和文档 -> 给出小步修改 -> 用户执行 -> AI 检查”的节奏。

项目本身是 Expo Router + React Native + 本地 SQLite 的 local-first 应用。用户数据保存在本地账号工作区中，后端无法也不应该直接读取手机 SQLite。因此 AI 助手不能设计成“后端查数据库再回答”，而是设计为：

1. 移动端收集用户问题。
2. 移动端 `AIAssistantService` 维护 ReAct 循环。
3. 移动端把 `messages + tools` 发给 FastAPI 后端。
4. 后端 LLM 返回 `tool_calls` 或最终 `text`。
5. 移动端执行本地 repository 工具，把工具结果再发回 LLM。
6. LLM 基于工具结果生成最终回答。

这个架构满足项目文档中“LLM 是大脑，Agent 是手脚，LLM 不直接接触数据库”的要求。

## 2. 分支与 CI 前置问题

### 2.1 检查 `feature/ai` 与 `dev` 的关系

开发前先检查了本地 `feature/ai` 和 `dev` 是否一致、是否包含最新 `dev`。后续多次合并 `origin/dev` 到 `feature/ai`，确保 AI 分支基于团队最新代码继续开发。

后期 PR 前再次检查：

- `feature/ai` 与 `origin/feature/ai` 对齐。
- 工作区和暂存区干净。
- `origin/dev` 是当前 `HEAD` 的祖先，说明 PR 分支已包含最新 `dev`。

### 2.2 `postJson` 引发 CI 不稳定

早期在 `src/data/api-client.ts` 中为了复用请求逻辑加入过 `postJson` helper，但推到远端后 CI 失败。判断原因可能是团队已有实现方式、接口代码风格或 lint/typecheck 对新增 helper 的约束和当前分支不一致。

处理方式：

- 删除 `postJson`。
- 将 `ApiClient.chat` 写成直接内联 `fetch`。
- 保持改动范围更小，避免和团队后续 API 实现冲突。

结论：`postJson` 只是便利性抽象，不是 AI 助手必需能力，删除不会影响当前 AI 功能。

### 2.3 Expo 依赖版本冲突与 lint 问题

团队在 `dev` 中选择了：

- `expo-asset`: `~55.0.17`
- `expo-audio`: `~55.0.14`

合并最新 `dev` 后，lint 一度无法通过。最终确认依赖已安装，但 ESLint 的 import resolver 对部分 Expo 包解析存在问题。

处理方式：

在 `eslint.config.js` 中为 import/no-unresolved 增加忽略项：

- `^react-native-webview$`
- `^expo-asset$`
- `^expo-audio$`

结果：lint 恢复为 `0 errors`，但仍有 8 个旧 warning，均非 AI 助手相关。

## 3. FastAPI 后端最小实现

### 3.1 创建后端目录

在项目根目录创建 `backend/`：

- `backend/requirements.txt`
- `backend/app/__init__.py`
- `backend/app/schemas.py`
- `backend/app/llm_client.py`
- `backend/app/main.py`

### 3.2 后端接口

实现两个接口：

- `GET /health`
- `POST /api/v1/ai/chat`

`/api/v1/ai/chat` 统一返回：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

`data` 支持两种类型：

- `{ "kind": "text", "content": "..." }`
- `{ "kind": "tool_calls", "tool_calls": [...] }`

### 3.3 Mock LLM

第一版后端先使用 `MockLLMClient`，避免一开始就接真实大模型导致调试变量过多。

Mock 行为：

- 用户问统计类问题时返回 `countPersons` / `countEvents`。
- 用户问人物相关问题时返回 `searchPersons`。
- 用户问事件相关问题时返回 `searchEvents`。
- 如果 messages 中已经包含 `tool` 消息，则返回最终文本。

这样可以先验证移动端 Agent 循环和工具调用链是否通畅。

### 4.2 扩展错误码

在 `src/domain/errors/app-error.ts` 中新增 AI/API 相关错误码：

- `NETWORK_ERROR`
- `API_RESPONSE_INVALID`
- `API_REQUEST_FAILED`
- `AI_EMPTY_QUESTION`
- `AI_UNKNOWN_TOOL`
- `AI_TOOL_ARGUMENT_INVALID`

这些错误码用于把网络失败、后端响应格式错误、工具参数错误等问题统一转换成可展示的应用错误。

### 4.3 实现 `ApiClient.chat`

`src/data/api-client.ts` 实现 `chat()`，请求：

```txt
POST /api/v1/ai/chat
```

后续又对 `ApiClient.chat` 做了加固：

- `fetch` 失败转成 `NETWORK_ERROR`。
- `response.json()` 失败转成 `API_RESPONSE_INVALID`。
- 后端返回 `code != 0` 或 HTTP 非 2xx 时转成 `AppError`。
- 校验 `data.kind`、`content`、`tool_calls` 和每个 tool call 的形状。

这个处理避免前端收到脏响应后在业务层深处崩溃。

## 5. AI 助手功能层实现

### 5.1 新增 AI feature 模块

新增：

- `src/features/ai-assistant/ai-assistant.vo.ts`
- `src/features/ai-assistant/ai-assistant-tools.ts`
- `src/features/ai-assistant/ai-assistant-service.ts`
- `src/features/ai-assistant/use-ai-assistant.ts`

### 5.2 工具定义

第一版工具包括：

- `searchPersons`
- `searchEvents`
- `getPersonDetail`
- `getEventDetail`
- `getPersonRelations`
- `getEventsByPerson`
- `getEventsByDateRange`
- `countPersons`
- `countEvents`
- `getDaysUsed`

后续为了支持“哪些事件让我最开心”这类问题，新增：

- `getEventsByEmotion`

### 5.3 Agent 循环

`AIAssistantService.ask(question)` 的核心逻辑：

1. 校验空问题，空问题抛 `AI_EMPTY_QUESTION`。
2. 构造 system prompt 和 user message。
3. 最多执行 5 轮。
4. 每轮调用 `apiClient.chat(messages, AI_ASSISTANT_TOOLS)`。
5. 如果返回 `text`，直接结束。
6. 如果返回 `tool_calls`，移动端执行本地工具，把结果作为 `tool` message 追加。
7. 超过最大轮次返回兜底回答。

### 5.4 本地工具执行

工具通过 `requireAccountRuntime()` 读取当前账号 runtime，再调用本地 repositories。这样 LLM 只看到工具结果，不直接接触数据库。

比较重要的工具结果：

- 人物只暴露 `{ personId, name }`。
- 事件摘要只暴露 `{ eventId, title, occurredAt }`。
- 事件详情包含参与者、分支、情绪。
- 人物详情包含关系边和关联事件 ID。

### 5.5 情绪查询工具的性能权衡

`getEventsByEmotion` 当前没有修改 repository 接口，而是：

1. 读取活跃情绪列表。
2. 根据别名匹配情绪名，例如“高兴/快乐”匹配“开心”。
3. 读取活跃事件列表。
4. 对每个事件调用 `eventEmotionRepo.findByEventId`。
5. 过滤出包含目标情绪的事件。

这是为了控制 MVP 改动范围。后续如果数据量变大，应在 repository 层补 `findByEmotionId` 或批量查询能力。

### 6.2 键盘遮挡问题

真机测试发现点击输入框后，输入框和发送按钮会被键盘遮挡，且多行输入高度不符合预期。

原因：

- Android 上 `KeyboardAvoidingView` 的 `behavior` 原来是 `undefined`。
- 多行 `TextInput` 没有明确设置 `textAlignVertical` 和滚动行为。
- 输入框高度上限没有精确限制到约 4 行。

处理：

- Android 使用 `behavior="height"`。
- `TextInput` 增加 `multiline`、`textAlignVertical="top"`、`scrollEnabled`。
- 输入框设置 `maxHeight: 112`，约 4 行内容。

结果：USB 真机测试中输入框和发送按钮可以保持在键盘上方。

### 6.3 后续发现：复制与 Markdown 渲染问题

真实 LLM 接入后，AI 回复会包含 Markdown，例如列表、加粗、代码块等。当前 UI 仍按普通 `Text` 渲染，因此 Markdown 没有正确展示。

同时聊天内容应支持复制。仅依赖 `Text selectable` 不够稳定，建议后续：

- 安装 `expo-clipboard`。
- 安装 `react-native-markdown-display`。
- 用户消息和 AI 回复都提供复制按钮。
- AI 回复使用 Markdown 组件渲染，复制按钮复制原始 Markdown 文本。

这是当前尚待完成的 UI 体验问题。

## 8. 后端错误统一

早期如果 LLM provider 出错，FastAPI 会返回默认异常响应，格式不符合移动端约定。

处理：

- 在 `backend/app/main.py` 中捕获 `create_llm_client()` 和 `llm_client.chat()` 的异常。
- HTTP 状态码返回 503。
- body 返回统一结构：

```json
{
  "code": 10001,
  "message": "AI assistant service unavailable.",
  "data": null
}
```

意义：

- 移动端 `ApiClient.chat` 可以稳定解析。
- UI 可以展示统一错误。
- 后续真实大模型网络失败、key 错误、模型异常时不会破坏前端协议。

## 9. 本地真机联调问题

### 9.1 最初的 base URL 问题

`.env.development` 原来是：

```txt
EXPO_PUBLIC_API_BASE_URL=http://localhost:3000
```

但 FastAPI 后端运行在 8000，因此移动端会请求错地址。

### 9.2 Android 真机 USB 调试方案

实际开发方式是：

1. Android 真机 USB 连接电脑。
2. 运行 `npx expo start`。
3. 切换到 Android 模式，在真机查看效果。

这种情况下不能使用 Android 模拟器的 `10.0.2.2`。更稳定的方案是：

移动端配置：

```txt
EXPO_PUBLIC_API_BASE_URL=http://127.0.0.1:8000
```

后端启动：

```powershell
python -m uvicorn app.main:app --reload --app-dir backend --host 127.0.0.1 --port 8000
```

端口反向代理：

```powershell
adb reverse tcp:8000 tcp:8000
```

这样手机访问自己的 `127.0.0.1:8000` 时，会通过 USB 转发到电脑上的 FastAPI。

### 9.3 CORS

后端建议加 CORS middleware。原生 Android 请求不主要依赖 CORS，但 Expo Web 或浏览器调试会用到。

## 10. 真实 LLM 接入

### 10.1 Provider 设计

后端从纯 mock 扩展为可切换 provider：

- 默认 `mock`。
- 配置环境变量后走 `openai_compatible`。

这样 DeepSeek、OpenAI、阿里百炼兼容模式等 OpenAI-compatible API 都可以接入。

### 10.2 后端私密配置

真实 LLM key 放在：

```txt
backend/.env.local
```

示例：

```txt
LIFEGRAPH_LLM_PROVIDER=openai_compatible
LIFEGRAPH_LLM_BASE_URL=服务商 base url
LIFEGRAPH_LLM_API_KEY=API key
LIFEGRAPH_LLM_MODEL=模型名
```

强调：不能把 API key 放进 `.env.development`，因为 `EXPO_PUBLIC_` 变量会进入前端 bundle。

### 10.3 OpenAI-compatible 转换

后端负责把移动端协议转换成 OpenAI-compatible 格式：

- `messages` 转换成 chat messages。
- `tools` 转换成 function tools。
- assistant tool calls 转换成 OpenAI 的 `tool_calls` 格式。
- tool result 转换成 `role: "tool"` 消息。

后端再把模型响应解析回移动端统一格式：

- tool calls -> `{ kind: "tool_calls", tool_calls }`
- final answer -> `{ kind: "text", content }`

## 13. 重要经验总结

1. AI 助手不能让后端直接访问本地 SQLite。移动端 Agent 执行工具是这个项目最合理的架构。

2. 不要过早抽象 API 请求 helper。`postJson` 在团队协作中引发 CI 不稳定，MVP 阶段更适合小范围、直接实现。

3. 后端要统一错误协议。真实 LLM 接入后，网络、key、模型格式都可能失败，必须保证移动端收到稳定 JSON。

4. 真机联调要区分模拟器和 USB 真机。USB 真机推荐 `adb reverse tcp:8000 tcp:8000`。

5. LLM provider 配置必须放后端 `.env.local`，不能放 Expo 前端环境变量。

6. 测试必须先锁协议，再接真实模型。mock 后端和 ApiClient 测试保证真实 LLM 接入不会破坏移动端协议。

7. Markdown 和复制属于真实 LLM 接入后才明显暴露的体验问题，应尽快补上。
