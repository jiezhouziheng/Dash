### **环境准备**

首先依赖文件（requirements.txt）要加上 `openai` 并pip安装，然后新建 `.env` 文件（当然这个文件要在 `gitignore` 里忽略，为了保护密钥）：&#x20;

```python
OPENAI_API_KEY=你的 API Key
OPENAI_MODEL=gpt-5.2
OPENAI_BASE_URL=
# base_url 先允许为空，是为了兼容两种情况：
# OPENAI_BASE_URL 为空 -> 使用 OpenAI 官方 API
# OPENAI_BASE_URL 有值 -> 使用兼容 OpenAI 协议的服务
```

为了读取环境变量，在 llm/client.py 中添加：

from dotenv import load\_dotenv

load\_dotenv() 的作用是读取项目根目录的 .env，把里面的配置加载到环境变量里。os.getenv("OPENAI\_API\_KEY") 的作用是从环境变量读取密钥，而不是把密钥写死在代码里。

OpenAI 官方 Python SDK 的推荐基础形态是通过 SDK 创建 client，再用 Responses API 创建模型响应，所以在\_\_init\_\_方法中我保留了两种实现：

1. 没有 OPENAI\_API\_KEY -> self.client = None（依旧返回占位实现）

2. 有 OPENAI\_API\_KEY -> 创建 OpenAI SDK client

### **client.py 三个函数提取**

在接真实 LLM 之前，我还要做集中占位输出，之前的 summary、learning\_plan、glossary 分散在 3 个方法里，这样一次请求会调用3次大模型，费token、费时间、输出不稳定。现在要把它们合到一个内部方法里，这样后面真实模型调用也可以返回同样结构：

```python
_placeholder_analysis()
  -> summary
  -> learning_plan
  -> glossary
```

这样统一了数据边界，让后面的真实模型调用更容易接进来，也更容易测试。同时我发现 PaperService 还在分别调用三个方法，这不合适，我新增了方法 `analyze_paper()` ，一次返回完整结果。旧的三个方法暂时保留，是为了兼容测试或以后别的地方可能还会用到。等项目稳定后，可以再决定删不删。

### **LLM输出校验**&#x20;

在 LLMClient 前新增了如下类，让LLM输出满足 schema ，而不是随意返回一段中文：

```python
class LLMAnalysisResult(BaseModel):
    summary: Summary
    learning_plan: list[LearningTask]
    glossary: list[GlossaryItem]
```

这是重要的 **schema-first 思路**：LLM 输出不能直接污染系统，必须先被 Pydantic 校验。

### **论文分析Prompt构造**&#x20;

新增了 \_trim\_text() 做字符截断（初级实现，后续改为 先 chunks -> 选前若干关键 chunks -> 再给 LLM），防止上下文爆炸。

新增 \_build\_analysis\_prompt 做 Prompt 构造。Prompt 初步设计如下：

```python
你是一个科研论文阅读助手。请基于用户提供的论文标题、摘要和正文，生成中文结构化分析。

要求：
1. 只基于输入内容分析，不要编造论文中没有的信息。
2. 如果信息不足，请明确写“原文信息不足”。
3. summary 需要覆盖研究问题、方法、贡献、局限。
4. learning_plan 给出 3 到 5 个学习任务，任务要具体、可执行。
5. glossary 提取 3 到 8 个关键术语，并用适合本科生理解的语言解释。
6. 输出必须符合系统要求的结构，不要输出额外说明。

论文标题：
{title or "未命名论文"}

论文摘要：
{abstract or "无摘要"}

论文正文 Markdown：
{body or "无正文"}
```

在这里明确了几条约束，更好地服务于论文阅读的主任务。

### **真实 LLM 生成函数**

新增 \_generate\_analysis\_with\_llm()，这是真实调用 LLM 生成内容的关键函数，其中用了`responses.parse()`，不是让模型返回一段普通文本再手动`json.loads()`。这样模型输出会直接按 LLMAnalysisResult（前面提到的LLM输出校验类）解析，LLMAnalysisResult 又复用了 Summary / LearningTask / GlossaryItem，解析失败会暴露为错误，而不是没有提示地写入坏数据。

现在模型输出的链路：

```python
LLM raw output
-> LLMAnalysisResult
-> Summary / LearningTask / GlossaryItem
-> PaperAnalysisResult
-> analysis.json / reading_note.md / frontend
```

这是重要的**工程边界**：LLM 可以生成内容，但不能绕过 schema。

### **测试暴露出的问题**

在写完真实 LLM 生成函数后的测试中，由于我在 `.env` 中的占位`OPENAI_API_KEY=你的 API Key`，代码看到 OPENAI\_API\_KEY 非空，就认为可以调用真实 API，于是 OpenAI SDK 试图构造 client，测试失败。这个问题很重要，暴露出来两个不足：

1. 占位 API Key 不应该被当成真实 Key

2. pytest 不应该因为本机 .env 存在就调用真实 LLM

所以我在\_\_init\_\_函数之前加了个 Key 的有效性判断函数，避免占位符触发真实请求。

再做**测试隔离，**&#x751F;产环境用真实 LLMClient，测试环境用 FakeLLMClient，即使以后填了真实 Key，pytest 也不应该误调 API。

在 tests 里涉及 LLM 调用的测试，都加上 FakeLLMClient 类，显然在工程上是不友好的。所以我要把 fake LLM 提取成测试共享 fixture，新建`tests/conftest.py`，**conftest.py 是 pytest 的共享测试配置文件。**&#x653E;在这里的 fixture，可以被同目录下所有测试文件直接使用，无需 import，以达到 fake\_llm\_client 的复用。

### 给 LLM 调用加错误兜底

真实 API 会有很多不稳定因素：

`Key 失效、模型名无权限、网络断开、限流、结构化输出解析失败、服务临时不可用`，如果这些错误直接抛出，/api/papers/analyze 就会 500，整条论文处理链路中断。更合理的是，LLM 成功 -> 使用真实分析，否则 -> 回退占位分析。

**兜底策略要放在边界层。**&#x50;aperService 不应该知道 OpenAI 的错误类型，也不应该处理网络错误；这些都属于 LLMClient 的职责。
