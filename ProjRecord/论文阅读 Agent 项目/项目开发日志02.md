# Paper-Reading-Agent 开发日志 02：从最小 MVP 到可检索问答闭环

日期：2026-05-23

## 1. 本阶段目标

本阶段的目标不是直接接入大模型，而是把 Paper-Reading-Agent 从一个“能跑通的演示原型”推进到一个更适合继续迭代、也更适合写进简历的工程型 Agent 项目。

初始版本已经具备最小闭环：

```text
前端输入标题、摘要、Markdown 正文
  -> FastAPI 接口接收请求
  -> PaperService 编排流程
  -> LLMClient 返回占位结果
  -> FileStore 保存 analysis.json 和 reading_note.md
  -> 前端展示结果
```

因此，本阶段采用“先建立结构，再增强智能”的策略：先把测试、schema、解析、分块、检索、问答接口和前端状态流打通，为后续接入真实 LLM 和向量检索打基础。

## 2. 关键成果

### 2.1 建立 pytest 测试体系

新增后端测试目录和测试配置：

```text
backend/tests/
backend/pytest.ini
```

当前测试覆盖：

- FastAPI 健康检查。
- 论文分析 API。
- `PaperService.analyze()` 的工作区创建和文件落盘。
- 输入校验。
- Markdown 章节解析。
- 文本分块。
- 阅读笔记渲染。
- 论文问答服务。
- 关键词检索模块。

这一步的价值在于，项目开始具备“可重构”的基础。后续拆模块、改 schema、换检索方式时，测试能及时告诉我们是否破坏了主流程。

### 2.2 固定后端输入和输出 schema

新增：

```text
backend/app/schemas/paper.py
```

定义了核心数据结构：

- `PaperAnalysisResult`
- `SourceInfo`
- `MarkdownSection`
- `TextChunk`
- `Summary`
- `LearningTask`
- `GlossaryItem`
- `PaperQuestionAnswer`
- `AnswerCitation`

设计思路：

- API 返回、服务层结果和 JSON 落盘应使用同一组结构，而不是各写各的 dict。
- Pydantic schema 相当于项目内部的数据合同。
- 当后续接真实 LLM 时，LLM 输出也要被校验成这些结构，避免不稳定文本直接污染系统。

这一步后，`PaperService.analyze()` 不再返回普通 dict，而是返回 `PaperAnalysisResult`。FastAPI 路由也声明了 `response_model`，使接口结构更明确。

### 2.3 改进输入校验和 paper_id 生成

新增校验规则：

- `abstract` 和 `markdown_body` 不能同时为空。
- 用户问题不能为空。

`paper_id` 从原来的“标题 slug + 秒级时间戳”升级为：

```text
<title-slug>-<YYYYMMDD-HHMMSS>-<uuid8>
```

这样解决两个问题：

- 同一秒提交同一标题时不容易冲突。
- 中文标题无法生成英文 slug 时，使用 `paper` 作为兜底前缀，避免退化成 `untitled-paper`。

这里的设计取舍是：`paper_id` 不追求完整表达论文标题，而优先保证可用、稳定和不冲突。后续如果引入 SQLite，可以把中文标题完整保存在元数据中，`paper_id` 只承担机器标识。

### 2.4 保存 Markdown 正文并解析章节

新增：

```text
backend/app/parsers/markdown_parser.py
```

系统现在会把用户输入的 Markdown 正文保存为：

```text
data/papers/<paper_id>/paper.md
```

并解析 Markdown 标题，生成 `sections`：

```json
{
  "order": 1,
  "title": "Method",
  "level": 1,
  "char_count": 48
}
```

这一步的意义是把“正文文本”从一次性输入变成可复用资产。后续问答、摘要、引用定位、PDF 解析结果都可以围绕统一的文档结构继续扩展。

### 2.5 增加文本分块 chunks

新增：

```text
backend/app/parsers/chunking.py
```

系统现在会把 Markdown 正文切分成可检索片段，并保存到：

```text
data/outputs/<paper_id>/chunks.json
```

chunk 的结构包括：

- `chunk_id`
- `section_title`
- `section_level`
- `order`
- `text`
- `char_count`

设计思路：

- 后续 RAG 不应该让模型直接读完整论文。
- 应先把论文切成 chunks，再按问题检索相关片段。
- 当前先使用简单段落分块，确保数据流打通。
- 章节归属目前较粗略，后续可以优化为按 section 精确切分。

这一步是从“论文分析工具”走向“RAG 型论文 Agent”的关键基础。

### 2.6 抽离阅读笔记渲染

新增：

```text
backend/app/renderers/reading_note.py
```

之前 `PaperService` 直接拼接 Markdown 字符串，这会让服务层越来越臃肿。现在改成：

```text
PaperService 负责流程编排
Reading note renderer 负责输出格式
```

生成的 `reading_note.md` 有稳定结构：

- 基本信息
- 摘要
- 论文总结
- 章节结构
- 术语表
- 学习计划
- 文件位置

这样做的好处：

- 输出格式集中维护。
- 服务层更清晰。
- 后续可以增加独立的学习计划 renderer、术语表 renderer、问答历史 renderer。

### 2.7 增加最小论文问答接口

新增接口：

```http
POST /api/papers/{paper_id}/ask
```

问答流程：

```text
用户问题
  -> 根据 paper_id 找到 chunks.json
  -> 读取 TextChunk 列表
  -> 检索相关 chunks
  -> 返回 answer 和 citations
```

当前答案是模板化回答，不是 LLM 生成：

```text
根据当前检索到的论文片段，相关内容主要集中在：Method
```

但返回结果包含引用片段：

```json
{
  "chunk_id": "chunk-0001",
  "section_title": "Method",
  "text": "Attention computes weighted token representations.",
  "score": 1
}
```

这体现了论文阅读 Agent 的核心要求：回答要能追溯。即使当前回答还不智能，也先把可解释性边界做出来。

### 2.8 抽离关键词检索模块

新增：

```text
backend/app/retrieval/keyword_retriever.py
```

最初检索逻辑写在 `PaperService._retrieve_relevant_chunks()` 中。后来拆成 `KeywordRetriever`：

```text
PaperService.ask()
  -> self.retriever.retrieve(question, chunks)
```

设计原因：

- 服务层应该编排流程，不应该承载具体检索算法。
- 关键词检索只是临时实现，后续会替换为向量检索。
- 抽离后，可以新增 `VectorRetriever`，而不影响 API 和问答主流程。

当前关键词检索的 `score` 是问题关键词在 chunk 文本中的命中数量，不代表置信度，也不是语义相似度。

### 2.9 前端接入问答流程

前端新增论文问答区域：

- 分析成功前，问答按钮禁用。
- 分析成功后，前端保存当前 `paper_id`。
- 用户提问时，前端调用 `/api/papers/{paper_id}/ask`。
- 页面展示回答和引用片段。

关键状态：

```js
let currentPaperId = null;
```

这个状态体现了前端工作流：

```text
生成分析 -> 获得 paper_id -> 基于当前 paper_id 提问
```

这个设计为后续多论文管理提供了自然扩展点：以后可以把 `currentPaperId` 变成“当前选中的论文”。

## 限制

但这个闭环仍然有几个明显不足：

- 没有测试体系，后续改动缺少反馈。
- 请求和响应结构主要依赖松散 dict，接口合同不够稳定。
- Markdown 正文只统计字符数，没有真正参与系统流程。
- 阅读笔记直接在服务层拼字符串，职责混杂。
- 没有可检索文本片段，无法支撑后续 RAG。
- 问答只是规划中的功能，尚未形成数据流。
- 前端只能分析论文，不能围绕当前论文继续提问。

## 3. 遇到的问题与解决思路

### 3.1 PowerShell 默认编码导致中文显示乱码

问题表现：

最初读取 README 和源码时，中文在终端中显示为乱码。

原因：

PowerShell 默认编码和文件 UTF-8 编码不一致。

解决：

使用显式 UTF-8 读取：

```powershell
Get-Content -Encoding UTF8 -Raw README.md
```

经验：

项目中文文档和中文字符串较多，后续读写文件时应明确使用 UTF-8，Python 中也统一使用 `encoding="utf-8"`。

### 3.2 pytest 的 tmp_path 在 Windows 上遇到权限问题

问题表现：

测试中大量 `tmp_path` fixture 报错：

```text
PermissionError: C:\Users\Lenovo\AppData\Local\Temp\pytest-of-Lenovo
```

同时 pytest cache 写入 `.pytest_cache` 也出现权限问题。

原因：

当前 Windows 环境对系统临时目录或 pytest 缓存目录存在访问限制。

解决：

新增 `backend/pytest.ini`：

```ini
[pytest]
testpaths = tests
pythonpath = .
addopts = --basetemp=.pytest_tmp_run -p no:cacheprovider
```

说明：

- `--basetemp=.pytest_tmp_run` 让 pytest 在项目内创建临时目录，不依赖系统 Temp。
- `-p no:cacheprovider` 关闭 pytest 缓存插件，避免 `.pytest_cache` 写入问题。
- `.pytest_tmp_run/` 和 `.pytest_cache/` 加入 `.gitignore`。

经验：

测试环境本身也是工程的一部分。一个稳定的 Agent 项目不只要业务代码能跑，还要测试在本机环境中可靠运行。

### 3.3 从项目根目录运行 pytest 时找不到 app 模块

问题表现：

在 `backend` 目录运行测试正常，但从项目根目录运行：

```powershell
python -m pytest backend
```

会报：

```text
ModuleNotFoundError: No module named 'app'
```

原因：

测试中使用：

```python
from app.services.paper_service import PaperService
```

当工作目录是 `backend` 时，Python 可以找到 `backend/app`。但当工作目录是项目根目录时，Python 会找 `Paper-Reading-Agent/app`，因此失败。

解决：

在 `pytest.ini` 中加入：

```ini
pythonpath = .
```

这里的 `.` 相对于 `backend/pytest.ini` 所在目录，也就是把 `backend` 加入模块搜索路径。

经验：

测试命令应尽量对运行位置不敏感，降低协作和 CI 环境中的踩坑概率。

### 3.4 chunking 测试失败：没有 sections 时直接返回整篇正文

问题表现：

测试期望长文本被切成多个 chunks：

```python
markdown = "A" * 20 + "\n\n" + "B" * 20 + "\n\n" + "C" * 20
chunks = build_text_chunks(markdown, [], max_chars=30)
assert len(chunks) == 3
```

但实际只返回 1 个 chunk。

原因：

最初逻辑中，如果 `sections` 为空，就直接返回完整正文 chunk，绕过了后面的 `max_chars` 分块逻辑。

解决：

改成“没有章节时创建默认章节 `正文`，但仍然走统一分块逻辑”：

```python
current_section = sections[0] if sections else MarkdownSection(
    order=1,
    title="正文",
    level=0,
    char_count=len(text),
)
```

经验：

特殊情况不应该绕过核心规则。没有 Markdown 标题只是缺少章节信息，不代表不需要分块。

### 3.5 API 测试污染真实 data 目录

问题：

如果 API 路由直接使用全局 `PaperService()`，测试会写入真实 `data/outputs`。

解决：

通过 FastAPI dependency override 注入测试专用 `FileStore(root_dir=tmp_path)`。

设计意义：

- 生产代码默认写真实 data 目录。
- 测试代码写临时目录。
- 测试运行后不污染用户数据。

经验：

可注入依赖是测试友好设计。后续接 LLM 时也应使用依赖注入或配置隔离，避免测试误调真实 API。

## 4. 设计思考

### 4.1 为什么先做 schema，而不是先接大模型

真实 LLM 输出天然不稳定。如果系统内部没有固定 schema，就会出现：

- 前端不知道字段是否存在。
- JSON 落盘结构经常变化。
- 测试难以编写。
- 后续检索、问答、笔记生成互相耦合。

因此先定义 `PaperAnalysisResult`、`TextChunk`、`PaperQuestionAnswer` 等结构，相当于先确定系统内部协议。等接入 LLM 时，只需要把模型输出转换并校验到这些 schema。

这体现了一个重要工程原则：先固定边界，再增强能力。

### 4.2 为什么先做关键词检索，而不是直接向量数据库

向量检索更强，但会引入额外复杂度：

- embedding 模型选择。
- 向量库依赖。
- 索引持久化。
- 相似度阈值。
- 召回质量评估。

当前阶段更重要的是把 RAG 主链路打通：

```text
文档 -> chunks -> retriever -> citations -> answer
```

关键词检索虽然简单，但它稳定、可解释、易测试。只要 `PaperService.ask()` 依赖的是检索器接口而不是具体算法，后续替换为向量检索的成本就可控。

### 4.3 为什么把阅读笔记渲染从服务层拆出去

服务层的职责是编排，不是格式化输出。如果把 Markdown 拼接写在 `PaperService` 里，后续会出现：

- 服务层越来越长。
- 输出格式修改容易影响业务流程。
- 难以单独测试阅读笔记格式。

拆出 `render_reading_note()` 后，阅读笔记成为独立输出能力，可以单独测试，也可以继续扩展。

### 4.4 为什么问答必须返回 citations

论文阅读 Agent 与普通聊天机器人不同。它的回答必须尽可能可追溯，否则用户无法判断结论是否来自论文。

当前系统即使没有真实 LLM，也要求问答返回：

- `chunk_id`
- `section_title`
- `text`
- `score`

这是后续做可信问答、引用高亮、跳转原文位置的基础。

### 4.5 为什么当前仍保留 LLMClient 占位

当前阶段没有急于接入真实大模型，是因为项目还在搭建基础架构：

- 输入校验。
- 数据结构。
- 文件落盘。
- Markdown 解析。
- chunking。
- retrieval。
- API。
- 前端状态。
- 测试。

等这些基础稳定后，接入真实 LLM 才不会变成“把 API 调用硬塞进服务层”。正确做法是让 `LLMClient` 成为模型供应商边界，后续替换 provider 时尽量只改这一层。

## 5. 当前架构快照

```text
frontend/index.html + main.js
  -> POST /api/papers/analyze
      -> PaperAnalyzeRequest
      -> PaperService.analyze()
          -> FileStore.prepare_paper_workspace()
          -> save paper.md
          -> parse_markdown_sections()
          -> build_text_chunks()
          -> LLMClient placeholder methods
          -> PaperAnalysisResult
          -> save analysis.json
          -> save chunks.json
          -> render_reading_note()
          -> save reading_note.md
      -> response_model=PaperAnalysisResult

  -> POST /api/papers/{paper_id}/ask
      -> PaperQuestionRequest
      -> PaperService.ask()
          -> FileStore.load_json(chunks.json)
          -> KeywordRetriever.retrieve()
          -> PaperQuestionAnswer
      -> response_model=PaperQuestionAnswer
```

可突出技术点：

- FastAPI API 设计。
- Pydantic schema 建模。
- 本地文件系统持久化。
- Markdown 解析和文本分块。
- RAG 前置链路设计。
- 关键词检索模块抽象。
- 可追溯问答 citations。
- pytest 测试和依赖注入。

## 7. 下一阶段计划

建议下一阶段继续按以下顺序推进：

1. 优化 chunking，使每个 chunk 精确归属到对应 Markdown section。
2. 保存问答历史到 `qa.json`，并写入 `analysis.json` 或独立文件。
3. 接入真实 LLM：先让 `LLMClient` 输出符合 Pydantic schema 的 JSON。
4. 将问答升级为“检索 chunks -> 构造 prompt -> LLM 基于引用片段回答”。
5. 增加 SQLite，保存论文元数据和历史记录。
6. 增加 PDF parser，把 PDF 解析结果转换为统一 Markdown/sections/chunks。
7. 引入向量检索，替换或增强 `KeywordRetriever`。
