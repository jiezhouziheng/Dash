### 确定最小可行版本后端 API 契约：

重要字段：

* paper\_id：每篇论文的唯一编号，后面保存文件、提问、查历史都靠它。

* summary：论文理解结果，先固定四项：研究问题、方法、贡献、局限。

* glossary：术语表，先做成列表，每个术语有名称和解释。

* learning\_plan：学习计划，先按阶段列任务。

* qa：问答记录，第一阶段可以先是空列表，后面再加“围绕当前论文提问”。

* artifacts：生成出来的文件位置。这个字段很重要，它让我知道系统到底把结果保存到了哪里。

**前端发什么 JSON**：title、abstract、body（PDF输入格式准备放在第二阶段）

**后端返回什么 JSON**：如“重要字段”所示，主要是论文的身份标识、用户期待的结果、问答记录（后续功能）以及清晰的生成文件位置。

**工程习惯**：改接口契约可以先小步验证，不必一次性把所有层都改完。

### 加深对 backend 的理解

```shell
前端
  -> routes.py 接收请求
    -> paper_service.py 编排流程
      -> client.py 生成内容
      -> file_store.py 保存文件
    -> routes.py 返回 JSON
  -> 前端展示结果
```

backend\app\\

**api\routes.py**：只负责 HTTP 接口，接收前端请求、校验请求字段、把请求交给 PaperService。

负责的字段：title、abstract、markdown\_body

**services\paper\_service.py**：项目核心，负责主流程编排。主要负责生成 paper\_id、判断 source\_type、调用 LLMClient 生成 summary / glossary / learning\_plan、调用 FileStore 保存结果、组装最终返回 JSON。

负责的字段：paper\_id、title、source\_type、summary、glossary、learning\_plan、qa、artifacts

**llm\client.py**：负责智能生成。初步预期提供生成论文总结、提取术语表、生成学习计划的功能。之后接 API 等 AI 功能主要在这里改。

负责的字段：summary、glossary、learning\_plan

**storage\file\_store.py**：负责本地文件和目录。存储相关在这里改。

负责的字段：artifacts

之后要加任何新功能，都先确认功能分类，这样保持对项目的整体把控。
